# 多光谱蓝牙通信协议 V4 实现说明

本文档描述 `projects/app_gatt` 当前固件的实际实现，用于区分传感器
I2C 数据、V4 应用协议帧、GATT Notification 和 BLE 空中数据包。

## 1. 端到端数据链路

下行控制链路：

```text
手机 APP
  -> FEE2 Write Without Response
  -> BK3633 校验 V4 命令
  -> 启动对应传感器任务
  -> 通过 I2C 配置并读取传感器
```

上行数据链路：

```text
传感器寄存器数据
  -> BK3633 组合为 uint16/int16 数据
  -> 组成 AA CMD DATA XOR BB
  -> 放入应用发送队列
  -> FEE4 Notify
  -> ATT/L2CAP/链路层传输
  -> 手机蓝牙栈重组
  -> APP 收到完整 HEX 特征值
```

单次读取与周期采集的区别：

```text
单次读取命令 0x42/0x44/0x46/0x48/0x4A
  -> 立即采集一次
  -> 通过 0x43/0x45/0x47/0x49/0x4B 返回

周期采集命令 0x4E
  -> 按周期采集
  -> 写入板载 W25Q64 的独立传感器分区
  -> APP 发送 0x50
  -> 通过 0x51 上传指定传感器的历史数据
```

## 2. BLE 通道

- 设备名：`SpectraVita`
- 服务 UUID：`0xFEE0`
- APP 向设备写命令：`0xFEE2`（Write Without Response/Write Command）
- 设备向 APP 回传：`0xFEE4`（Notify）
- APP 必须先打开 FEE4 Notify，再向 FEE2 发送命令。
- FEE2 的 Write Without Response 没有 ATT 写应答；业务应答由设备另行通过
  FEE4 Notify 返回。
- 固件连接后会主动请求 ATT MTU 交换，串口会输出协商结果
  `ind->mtu = ...`。

## 3. V4 应用协议帧

### 3.1 帧格式

```text
AA | CMD | DATA | XOR | BB
```

| 字段 | 长度 | 说明 |
| --- | ---: | --- |
| `AA` | 1 | 帧头 |
| `CMD` | 1 | 命令字 |
| `DATA` | 可变 | 命令参数或传感器数据 |
| `XOR` | 1 | `CMD` 与全部 `DATA` 字节的异或 |
| `BB` | 1 | 帧尾 |

异或校验不包含 `AA` 和 `BB`：

```text
XOR = CMD XOR DATA[0] XOR DATA[1] ...
```

例如：

```text
AA 48 03 4B BB

0x48 XOR 0x03 = 0x4B
```

多字节整数使用小端序。例如字节 `34 12` 表示 `uint16_t 0x1234`。

当前协议没有长度字段，也没有转义字段。设备依靠 BLE 特征值边界、命令规定的
固定长度以及请求上下文判断 DATA 长度。XOR 只是简单的应用层错误检测，不替代
BLE 链路层 CRC，也不具备安全认证能力。

### 3.2 已实现命令

| 请求 | 响应 | 功能 | 响应 DATA 长度 | 完整响应帧长度 |
| --- | --- | --- | ---: | ---: |
| `0x40` | `0x41` | 时间戳、电量、版本 | 6 | 10 |
| `0x42` | `0x43` | AS7341 手动多光谱 | 20 | 24 |
| `0x44` | `0x45` | AS7341 Flicker FIFO | 256 | 260 |
| `0x46` | `0x47` | AS7331 紫外 | 8 | 12 |
| `0x48` | `0x49` | WH4530A 接近 | 4 | 8 |
| `0x4A` | `0x4B` | ADXL345 加速度 | 6 | 10 |
| `0x4E` | `0x4F` | 启动周期采集 | 1 | 5 |
| `0x50` | `0x51` | 上传指定传感器历史数据 | 4 + N | 8 + N |
| `0x52` | `0x53` | 停止周期采集 | 0 | 4 |

经确认后的目标格式：

- APP 通过 `0x42` 手动指定多光谱增益，因此 `0x43` 只返回 20 字节光谱值，
  不再重复返回增益。当前固件已经按此格式实现。
- 周期采集属于多光谱自动模式，历史记录需要携带实际使用的增益，因此每组仍为
  22 字节。
- `0x49` 最终采用 4 字节，分别返回两个不同增益下的接近原始值 A 和 B。

## 4. 传感器采集与 DATA 格式

### 4.1 AS7341 多光谱：`0x42 -> 0x43`

请求 DATA：

```text
ATIME(1) | ASTEP(2，小端) | AGAIN(1)
```

手动读取响应 DATA 共 20 字节，由 10 个 `uint16_t` 组成：

```text
F1 | F2 | F3 | F4 | F5 | F6 | F7 | F8 | CLEAR | NIR
```

APP 已经在 `0x42` 中指定 `AGAIN`，因此 `0x43` 不再返回增益。周期自动采集的
多光谱历史记录则需要携带实际增益，格式为：

```text
GAIN(2) | F1 | F2 | F3 | F4 | F5 | F6 | F7 | F8 | CLEAR | NIR
```

周期记录共 22 字节。当前结构使用 `uint16_t` 保存 GAIN；若 APP 只按一个字节
解析增益，需要在最终协议中统一该字段宽度。

AS7341 分两次读取 F1～F4/CLEAR/NIR 和 F5～F8/CLEAR/NIR，之后组合成一组
多光谱快照。多光谱任务与 FIFO 任务共用 AS7341，固件使用互斥标志避免两者
同时访问。

### 4.2 AS7341 Flicker FIFO：`0x44 -> 0x45`

请求 DATA：

```text
FD_TIME(2，小端) | FD_GAIN(1)
```

FIFO 不是“普通多光谱数据太大”，而是 AS7341 闪烁检测通道的连续时间采样。
按官方数据手册 DS000504 v3-00，采样积分时间为：

```text
tINT_FD = FD_TIME × 2.78 µs
```

默认`FD_TIME=720`时，单点积分时间为2.0016 ms，采样率约499.6003 Hz；完成
128次积分约需256.2048 ms（从第1点到第128点的横轴跨度为127个间隔，约
254.2032 ms）。固件读取 128 个 `uint16_t`：

```text
FIFO1 | FIFO2 | ... | FIFO128
```

因此响应 DATA 固定为：

```text
128 × 2 = 256 字节
```

AS7341内部FIFO容量是128个两字节条目；第129个条目到达时置`STATUS6.FIFO_OV`，
新数据丢失，原有128点保留。`CFG1.FIFO_TH`只能把FINT阈值设为1/4/8/16，不能
配置128点中断，因此当前板级实现每10 ms读取`FIFO_LVL`并分段搬运到BK3633的
128点缓冲，累计满128点立即关闭FDEN。默认参数下正常约在第26个tick、约260 ms
完成；超时为`ceil(128×FD_TIME×2.78 µs / 10 ms)+10`个tick，默认36 tick即
360 ms。驱动会在读取前检查`STATUS6.FIFO_OV/FD_TRIG`并打印异常。

`CONTROL.FIFO_CLR`按数据手册使用bit1；bit2是`SP_MAN_AZ`，不能用于清FIFO。
正常路径始终返回完整128点。V4响应仍固定256字节且未新增有效长度字段；只有启动、
I²C或超时异常时，未收满的尾部才保留为0。这些数据可由APP/PC进一步进行频率或
闪烁分析。

### 4.3 AS7331 紫外：`0x46 -> 0x47`

请求 DATA 是 GAIN 档位编号。当前映射为：

| GAIN | 实际增益 | GAIN | 实际增益 |
| ---: | ---: | ---: | ---: |
| 0 | 1x | 6 | 64x |
| 1 | 2x | 7 | 128x |
| 2 | 4x | 8 | 256x |
| 3 | 8x | 9 | 512x |
| 4 | 16x | 10 | 1024x |
| 5 | 32x | 11 | 2048x |

GAIN 大于 11 时回退到档位 9，即 512x。响应 DATA 为：

```text
UVA(uint16) | UVB(uint16) | UVC(uint16) | Temperature(uint16)
```

共 8 字节。

### 4.4 WH4530A 接近：`0x48 -> 0x49`

命令中的 GAIN 只使用低 2 位：

| 低 2 位 | 实际增益 |
| ---: | ---: |
| 0 | 1x |
| 1 | 2x |
| 2 | 4x |
| 3 | 8x |

经确认，A 和 B 是两个不同增益下的接近值，用于降低单一增益测量不准的风险。
当前实现连续读取两次：

```text
接近 A：固定使用 GAIN=0（1x），作为基准值
接近 B：使用请求中的 GAIN 低2位（0/1/2/3对应1x/2x/4x/8x）
```

返回一个 `0x49` 帧，而不是两个返回帧：

```text
AA 49 A_L A_H B_L B_H XOR BB
```

`0x49` 最终采用 4 字节。当前变量名虽然使用 distance/proximity，但返回的是
传感器原始接近计数，不应直接当作毫米距离。当前代码为A固定1x、B使用APP指定增益。
历史记录仍只有A/B原始值，没有额外保存B的增益代码，因此解析历史时需要知道采集前
最后设置的接近增益。

### 4.5 ADXL345 加速度：`0x4A -> 0x4B`

请求无 DATA。响应为三个有符号 16 位原始值：

```text
ACC_X(int16) | ACC_Y(int16) | ACC_Z(int16)
```

共 6 字节，仍按小端序排列。

单次 `0x4A/0x4B` 的格式保持不变。只有 TYPE=5 的周期历史记录增加状态字节：

```text
STATE(1) | ACC_X(int16) | ACC_Y(int16) | ACC_Z(int16)
```

- `STATE=0x00`：LOW，ADXL345以Sleep/Wakeup 1 Hz实际采样，每组直接写入Flash；
- `STATE=0x01`：HIGH，ADXL345以50 Hz实际采样，全部样本经Stream FIFO写入Flash；
- LOW先保存2个1 Hz保护样本，再清除旧中断并开放Activity；初始阈值约0.31 g，命中后切换HIGH，保护期内的假触发不会切换；
- HIGH的FIFO Watermark为16；INT1/P20第一次进入ISR后立即被屏蔽，主循环每次最多读取8组，FIFO低于水位且INT1为低后重开，防止锁存源形成中断风暴；100 ms轮询继续补偿漏中断和屏蔽期事件；
- FIFO数据先进入128条RAM队列，再以最多8条为一个Flash批次；擦除、跨页正文、CRC和提交魔数通过非阻塞状态机逐步执行。`q<32`时20 ms推进，`q>=32`或排空时10 ms推进，回调只置待办；查询完成后同轮可发下一条命令，BLE仍在每一步前后调度；
- HIGH启用AC耦合XYZ硬件Inactivity，阈值寄存器3（约0.1875 g）、时间2秒；触发后冻结并排空再回到LOW；
- 软件兜底使用`max(|dx|,|dy|,|dz|)<30 LSB`连续100组（约2秒），与ADXL345逐轴判断一致；Activity触发前读取`ACT_TAP_STATUS`统计XYZ来源；
- HIGH退出、上传或`0x52`停止前先停止新样本并排空FIFO与RAM队列，不主动丢弃不足16组的数据；
- 若检测到FIFO溢出、I²C失败、RAM队列耗尽或Flash写入失败，加速度计划进入故障停机并打印统计；
- LOW保护样本数、Activity阈值、硬件Inactivity参数和软件安静计数集中在`config/acc_motion_config.h`；
- 上传结束且计划仍有效时，从LOW 1 Hz重新开始采集。

## 5. 周期采集和历史上传

### 5.1 启动周期采集：`0x4E -> 0x4F`

`0x4E` 完整帧长度固定为 15 字节，其 DATA 为：

```text
当前 Unix 时间戳(4，小端)
| 最小采集周期秒数(2，小端)
| 多光谱 X(1)
| FIFO X(1)
| 紫外 X(1)
| 接近 X(1)
| 加速度 X(1)
```

当前确认的五个 X 是独占的传感器选择位，不是周期倍数：

- `X=0`：不选择该位置对应的传感器。
- `X=1`：选择该位置对应的传感器并启动周期采集。
- 每条 `0x4E` 必须且只能有一个 X 为 1。
- 五个 X 全为 0、两个以上 X 为 1，或者任意 X 大于 1，均为非法配置，设备
  通过 `0x4F` 返回失败。

前面的“最小采集周期”字段虽然沿用协议中的名称，但当前语义是本条命令所选
传感器的实际采样周期，单位为秒。例如周期为 60 秒、X 为 `1,0,0,0,0` 时，
表示只启动多光谱，并且多光谱每 60 秒采集一次。

已确认的正式业务周期为：

| 传感器 | 采样周期 | 每天组数 |
| --- | ---: | ---: |
| 多光谱 | 60 秒 | 1440 |
| FIFO | 600 秒 | 144 |
| 紫外 | 60 秒 | 1440 |
| 接近 | 600 秒 | 144 |
| 加速度 | LOW实际1 Hz，HIGH实际50 Hz | 随运动时长变化 |

五种周期集中定义在：

```text
config/sensor_period_config.h
```

对应宏为：

```c
SENSOR_SAMPLE_PERIOD_MSS_S
SENSOR_SAMPLE_PERIOD_FIFO_S
SENSOR_SAMPLE_PERIOD_UV_S
SENSOR_SAMPLE_PERIOD_DIST_S
SENSOR_SAMPLE_PERIOD_ACC_S
```

当前 `SENSOR_SAMPLE_PERIOD_STRICT=1`，因此 `0x4E` 携带的周期必须与所选传感器
的配置宏一致，否则返回 `0x4F=1`。以后修改周期时只需修改该文件中的宏、重新
编译烧录，并让 APP 的 `0x4E` 使用相同周期。临时联调需要发送任意非零周期时，
可以将 `SENSOR_SAMPLE_PERIOD_STRICT` 改为 0。

一条 `0x4E` 只建立或更新“一个传感器 + 一个采样周期”的采集计划，但设备内部
分别保存五套计划。APP 连续发送五条各有一个 X=1 的 `0x4E` 后，五种传感器会
按照各自周期独立运行；后一条命令不会停止或覆盖前面已经配置的其他传感器。

使用示例时间戳 `0x12345678` 的完整命令为：

```text
AA 4E 78 56 34 12 3C 00 01 00 00 00 00 7B BB
```

`0x4F` 的执行结果：

```text
AA 4F 00 4F BB    周期配置成功
AA 4F 01 4E BB    周期配置失败
```

`0x00` 表示成功，部分 APP 如果把该字节直接显示为布尔值，可能显示为 `false`。
`0x4F=0` 只表示定时配置已接受，不表示传感器已经成功完成采样。周期为 0，
任意 X 不是 0/1，或者 X 中 1 的数量不等于一个时返回失败；失败时保留原采集
计划。停止周期采集统一使用 `0x52`，不使用全 0 的 `0x4E`。

收到新的 `0x4E` 时会：

1. 用命令时间戳校准设备软件时钟；
2. 找出唯一 X=1 的传感器；
3. 清空该传感器的历史缓存，不影响其他传感器；
4. 保存或更新该传感器的周期，并从零开始计算它的下一次采集；
5. 公共 1 秒调度器分别累计五种传感器的时间，到达各自周期后独立触发采集。

因此重新配置某一种传感器前应先上传该传感器的旧历史，否则它自己的旧数据会
被清除；其他四种传感器的计划和历史不受影响。

### 5.2 当前 W25Q64 一天历史

板载 W25Q64 容量为 8 MiB。前四种低速数据各分配256 KiB，其余7 MiB分给
变速加速度历史：

| 数据类型 | Flash分区 | 分区大小 | 正式周期每天组数 | 单组数据 |
| --- | ---: | ---: | ---: | ---: |
| 多光谱 | `0x000000` | 256 KiB | 1440 | 22 B |
| FIFO | `0x040000` | 256 KiB | 144 | 256 B |
| 紫外 | `0x080000` | 256 KiB | 1440 | 8 B |
| 接近 | `0x0C0000` | 256 KiB | 144 | 4 B |
| 加速度 | `0x100000` | 7 MiB | 动态 | 7 B |

加速度分区可保存约365364组。若全天都是LOW，1 Hz一天需要86400组；在此基础上约还能
容纳95分钟累计HIGH活动。若持续保持HIGH 50 Hz，则容量约为2小时，无法保存完整24小时。
因此当前方案适用于“高速运动间歇出现”的场景；若要求全天连续50 Hz，必须扩大Flash、
压缩记录或降低高速采样率。

每条 Flash 记录还保存 4 字节 Unix 时间戳、会话号、提交标志和 CRC16。每个分区
的第一扇区是日志头；数据扇区首次写入时才按需擦除。达到按命令周期计算的24小时
记录上限或物理容量后，不覆盖最早数据，并立即停止该传感器的周期计划；加速度会
同时停止 Stream。已有历史保持不变，等待 APP 上传并清除后，必须重新发送 `0x4E`
才能开始新的周期计划。单次查询命令不受影响。

有效日志在复位后会由记录魔数、会话号和 CRC 扫描恢复，因此断电不会像旧 RAM
版本那样直接丢失历史。收到新的 `0x4E` 会重建所选传感器的日志头，等同清空它
自己的旧历史，另外四种数据不受影响。

### 5.3 上传历史：`0x50 -> 0x51`

请求格式：

```text
AA 50 TYPE XOR BB
```

| TYPE | 数据类型 | 每组长度 |
| ---: | --- | ---: |
| `0x01` | 多光谱 | 22 |
| `0x02` | FIFO | 256 |
| `0x03` | 紫外 | 8 |
| `0x04` | 接近 | 4 |
| `0x05` | 加速度历史（状态+XYZ） | 7 |

TYPE=2的Flash物理槽位为268字节。底层保持一次W25Q读事务并按最多64字节分片接收；任一子块未完整读取即中止，CRC首次失败时从槽位起点完整重读一次。失败不会清除FIFO历史。

按当前协议字段，一条 `0x4E` 配置一种传感器，连续五条可建立五套独立周期计划。
一条 `0x50` 只携带一个 TYPE，因此只请求一种传感器历史。上传一天的五种数据时，
APP 必须采用“发送一个 `0x50`、等待该类型全部 `0x51` 上传完成、再请求下一种”
的串行流程。

现已确认上传对象为累计一天的历史数据，并且一次只传一种传感器。一次 `0x50`
应触发设备连续发送该 TYPE 的全部历史分包，直到这一天的该类数据上传完成；它
不是开启采集后持续实时推送新数据的开关。

协议没有定义一个 `0x51` 同时混装多种传感器数据。若后续需要混装，每个数据块
必须至少增加 `TYPE + LEN + COUNT`，否则 APP 无法判断各传感器的数据边界。

响应格式：

```text
AA 51 第一组Unix时间戳(4) 记录1 记录2 ... 记录N XOR BB
```

当前 `0x51` 响应没有携带 TYPE、记录数量、包序号和总包数。APP 必须记住刚才
`0x50` 请求的 TYPE，并按对应记录长度解析：

```text
记录数 = (完整 0x51 帧长度 - 8) / 单组长度
```

例如一个装有13组多光谱记录的满包为294字节：

```text
1(AA) + 1(51) + 4(时间戳) + 13×22(记录) + 1(XOR) + 1(BB)
= 294 字节
```

历史上传期间，周期定时器仍继续计数，但不会触发新的采集；上传期间错过的采集点
不会补采。发送队列清空后自动允许后续周期采集。

当前固件已经实现逐包状态机。一条 `0x50` 会连续发送多个 `0x51`，每一包收到
BLE协议栈成功响应后才读取并发送下一包。最后一包成功后才擦除该类型的日志头；
中途断线不清数据，重新连接后再次发送 `0x50` 会从第一包重传。

擦除采用“立即擦除日志头、旧数据扇区下次写入时按需物理擦除”的方式，避免上传
完成后同步擦除数百个扇区而长时间阻塞。若没有先发送 `0x52`，固件会建立下一天
的新日志并恢复原周期计划。

结合 Word 中“直到本地数据完全上传完毕”的描述，`0x50` 是启动一次有限的历史
批次传输，而不是永久开启未来采样数据的实时推流。

### 5.4 停止周期采集：`0x52 -> 0x53`

```text
APP -> 设备：AA 52 52 BB
设备 -> APP：AA 53 53 BB
```

停止命令关闭全部五种传感器的周期计划，但不会主动清除已经保存的历史数据。
之后仍可使用 `0x50` 逐种读取已有历史。

## 6. 应用帧、ATT Notification 和空中分片

“分包”需要区分三个层次。

### 6.1 V4 应用层

固件定义：

```text
APP_MSG_MAX_LEN = 300
PROTOCOL_TX_QUEUE_DEPTH = 4
```

- 单个 V4 完整帧最大 300 字节。
- 发送队列最多保存 4 个完整帧。
- 队列一次只向 FEE4 提交一个 Notification，完成后再发送下一帧。
- 当前没有把一个大 V4 帧主动拆成多个 V4 子包。

### 6.2 ATT/GATT 层

一个完整 V4 帧作为一次 FEE4 Notification 的特征值。Handle Value Notification
还需要 3 字节 ATT 开销，因此：

```text
特征值最大长度 = ATT_MTU - 3
需要的最小 ATT_MTU = V4 完整帧长度 + 3
```

| V4 帧 | 完整帧长度 | 最小 ATT MTU |
| --- | ---: | ---: |
| 单次 FIFO `0x45` | 260 | 263 |
| FIFO 历史 `0x51` | 264 | 267 |
| 12 组多光谱历史 `0x51` | 272 | 275 |

如果 MTU 太小，BLE 栈不会把一个超长特征值自动变成多次 FEE4 Notification。
需要兼容小 MTU 手机时，必须由应用协议实现分片发送。

### 6.3 L2CAP/控制器/链路层

在 ATT MTU 足够的前提下，一个 272 字节 FEE4 Notification 在空中仍可能被
L2CAP、HCI 或 BLE 控制器拆成多个链路层 Data PDU。手机蓝牙栈收到后自动重组，
所以通常表现为：

```text
手机 APP 日志：一条 272 字节 Receive Value
空口抓包：多条 BLE Data PDU
```

底层自动分片不等于应用层多包上传。APP 看到的是重组后的完整特征值。

## 7. 抓包和分层排查

### 7.1 I2C 逻辑分析仪：传感器到 BK3633

连接 `GND/SCL/SDA`，分析器输入电压必须兼容板上 I/O 电压，不能向 1.8 V 总线
注入 5 V。当前 I2C 配置为 100 kHz、7 位地址：

| 设备 | 7 位地址 |
| --- | ---: |
| AS7341 | `0x39` |
| AS7331 | `0x74`（硬件地址脚可能使其位于 `0x74～0x77`） |
| WH4530A | `0x38` |
| ADXL345 | `0x53` |

逻辑分析仪可以确认：

```text
START -> 地址+W -> 寄存器 -> 配置数据 -> ACK -> STOP
START -> 地址+R -> 传感器数据 -> ACK/NACK -> STOP
```

如果串口收到命令但 I2C 没有波形，应检查命令解析、任务状态、电源控制和引脚复用。

### 7.2 UART 日志：BK3633 应用内部

FEE2 收到命令时会输出连接索引、长度和完整 HEX。UART 日志适合检查：

- 命令是否进入设备；
- 长度/XOR 是否通过；
- 传感器 ID、初始化或测量是否超时；
- MTU 协商结果；
- 发送队列是否满。

UART 日志不是 BLE 空口抓包。

### 7.3 手机 GATT 工具：V4 应用层

手机工具显示的 FEE2 Write 和 FEE4 Receive Value 是蓝牙栈处理后的 GATT 特征值，
适合核对完整 V4 帧：

```text
FEE2：AA 48 00 48 BB
FEE4：AA 49 A_L A_H B_L B_H XOR BB
```

它通常看不到底层重传和链路层分片。

### 7.4 BLE 空口抓包

使用支持 BLE 嗅探的硬件和 Wireshark，从建立连接前开始抓包。常用显示过滤器：

```text
btle
btl2cap
btatt
```

重点观察：

- ATT Write Command：APP 写 FEE2；
- ATT Handle Value Notification：设备从 FEE4 返回；
- 一次大 Notification 对应的多个链路层数据 PDU；
- 重传、连接间隔和断开原因。

FEE2/FEE4 的属性 Handle 由服务发现结果决定，不应在抓包脚本中假定为固定值。

### 7.5 推荐联调顺序

```text
1. 手机日志确认 FEE2 写入内容正确
2. UART 确认 BK3633 收到并通过帧校验
3. I2C 抓包确认寄存器配置和读取正常
4. UART 确认传感器任务完成并进入发送队列
5. 手机确认 FEE4 收到完整帧并校验 XOR
6. 只有出现 MTU、重传或断连问题时再做 BLE 空口抓包
```

## 8. 接近传感器端到端示例

APP 发送：

```text
AA 48 00 48 BB
```

完整过程：

```text
1. APP 向 FEE2 写入 5 字节命令
2. BK3633 检查帧头、帧尾、长度和 XOR
3. 打开传感器电源并初始化 I2C
4. WH4530A 使用固定1x增益进行第一次测量
5. 读取 proximity A
6. WH4530A 切换到命令指定增益进行第二次测量
7. 读取 proximity B
8. 关闭传感器并允许低功耗
9. 组成 AA 49 A_L A_H B_L B_H XOR BB
10. 完整 8 字节帧进入发送队列
11. 通过一次 FEE4 Notification 提交给 BLE 栈
12. BLE 底层完成传输和必要的分片/重组
13. APP 收到一条 8 字节 Receive Value
```

## 10. 当前限制和待确认项

1. `0x49` 的 DATA 长度及接近 A/B 的业务定义需最终确认。
2. `0x51` 当前没有 TYPE、记录数、包序号、总包数和结束标志。
3. 当前只有 BLE 协议栈发送确认，没有 APP 数据已持久化的业务层 ACK。
4. 中途断线会保留 Flash 并支持从第一包重传，但不支持中间包断点续传。
5. 最大帧为300字节，需 ATT MTU 至少303；默认 MTU=23 的设备需要应用层分片。
6. V4 帧没有长度、序号和消息认证字段，后续升级协议时建议补充。
7. 外部 Flash 版本已编译通过，仍需实板验证 JEDEC、断电恢复和完整24小时上传。
8. 加速度LOW/HIGH阈值是初始工程值，仍需结合实物佩戴位置和动作数据标定。
9. 加速度HIGH为50 Hz，而`0x51`仍只有每包首组的Unix秒时间戳。状态字节可标明LOW/HIGH，
   但若APP必须恢复每组精确到20 ms的时间，还需增加毫秒时间、样本序号或固定批次边界。

## 11. 低功耗处理

- 无采集任务时关闭 `VDD_1P8_PIN` 和 `VDD_SENSOR_PIN` 电源域。
- AS7331 测量后进入 Power Down。
- ADXL345周期模式保持50 Hz低功耗测量并由Watermark唤醒MCU；停止或上传时进入Standby。
- AS7341 完成后关闭测量模块。
- 不再默认每秒连续采集；只有收到单次读取或 `0x4E` 后才工作。
- 历史上传期间暂停触发新的周期采集，发送队列清空后恢复。
- 连接指示灯只短闪，不在整个连接期间常亮。
- BLE 广播使用约2秒间隔；连接参数请求为30～50 ms、slave latency 0、监督超时10秒。
